# 实时数字人（LiveTalking + wav2lip）接入说明

这一层是**可选的**。没有它，平台依旧可用：历史人物页会退回到「画像开口说话」或静态画像，文字 / 语音对话不受影响。
（原先基于 Three.js + GLB 的 3D 数字人已整体移除，不再作为回退方案。）
接上它之后，历史人物卡片里显示的是一段**真人视频**，说话时由 wav2lip 实时改口型，通过 WebRTC 推到浏览器。

---

## 1. 它是怎么工作的

```
浏览器 <--WebRTC--> LiveTalking(app.py :8010) <--音频+文本--> 后端 FastAPI(:8000)
                          |
                          +-- data/avatars/<人物>_lt/   说话帧（wav2lip 在上面改口型）
                          +-- data/custom/<人物>_idle/  待机帧（静音时循环播放）
```

- 说话：素材视频逐帧导出成图片；每来一帧，模型只重绘**人脸区域**再贴回原帧，其余部分（身体、背景）直接复用素材帧。
- 待机：不说话时循环播放待机视频导出的帧序列，**不做模型推理**。
- 前端入口：`frontend/src/components/agent/LiveTalkingAvatar.vue`
- 人物映射：`frontend/src/views/FigureChat.vue` 里的 `LIVE_TALKING_AVATARS`

## 2. 前置条件

| 项目 | 要求 |
|---|---|
| 显卡 | NVIDIA GPU + 可用驱动（本项目开发机为 RTX 5060 Laptop 8G / 驱动 616.92） |
| Python | 3.10 / 3.11 独立环境 |
| PyTorch | CUDA 版本，需与驱动匹配 |
| 磁盘 | 每个数字人约 60–250 MB（帧序列） |

## 3. 安装

### 3.1 获取引擎代码并打上本地补丁

```powershell
cd <你的工作区父目录>            # 与 yuzhang-academy 同级
git clone https://gitee.com/lipku/LiveTalking.git
cd LiveTalking
git am ..\yuzhang-academy\docs\livetalking-patch\*.patch
```

补丁含四处本地改造，缺了会影响体验：

1. **待机画面只正放、不倒放** + 自定义动作配置（`app.py`、`avatars/base_avatar.py`、`server/routes.py`）
2. **限制 torch 算子线程池**（默认单线程），说话时进程 CPU 从 3.2 核降到 0.83 核
3. **推流码率上限 + 贴回质量**（`app.py`、`avatars/wav2lip_avatar.py`）：
   aiortc 默认 H.264 只有 1 Mbps、上限 3 Mbps，这里把起始码率提到 3 Mbps、上限 6 Mbps；
   贴回由默认线性插值改为 `INTER_AREA`，并在重绘区边缘加 4–12px alpha 羽化。
4. **按人物放大张嘴幅度**（`avatars/wav2lip_avatar.py` 的 `MOUTH_GAIN`）：
   对素材本身动作偏小的人物，按 `out = orig + gain*(gen - orig)` 放大下半张脸的变化量。

### 3.2 安装依赖

```powershell
conda create -n livetalking python=3.10 -y
conda activate livetalking
pip install -r requirements.txt
# torch 请按显卡驱动选择对应 CUDA 版本，例如：
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu124
```

### 3.3 放模型权重

`models/wav2lip.pth`（约 205 MB）与人脸检测权重 `avatars/wav2lip/face_detection/detection/sfd/s3fd.pth`（约 86 MB）需要自行下载后放到对应位置。
启动脚本会检查 `models/wav2lip.pth`，缺失时自动跳过数字人这一路。

## 4. 准备人物素材

每个人的素材是两段视频：**说话动作**和**待机动作**（本项目放在工作区的 `数字人/` 目录，不入库）。

### 4.1 说话帧（wav2lip 用）

先把原片统一缩到 480 宽（本项目所有人物都是 480 宽，帧数据体积与 CPU 开销最小；
720 宽能更清晰，但每帧贴合与 WebRTC 软编码的开销也要涨一倍多）：

```powershell
# ffmpeg 可以用 conda 环境里自带的：imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v7.1.exe
ffmpeg -i "数字人\罗从彦说话动作.mp4" -vf "scale=480:-2" -c:v libx264 -crf 18 -pix_fmt yuv420p -an "_tmp\luocongyan_talk_480.mp4"
```

再生成 avatar（**必须用 `-m` 以模块方式跑**，直接写脚本路径会因为 `avatars` 包不在 sys.path 而导入失败）：

```powershell
cd LiveTalking
python -m avatars.wav2lip.genavatar `
  --video_path "..\_tmp\luocongyan_talk_480.mp4" `
  --avatar_id luocongyan_lt --img_size 256
```

> ⚠️ 本机使用的是 `wav2lip_v2`，人脸裁切图必须是 **256×256**（务必带 `--img_size 256`）。
> 尺寸不匹配时说话会因为输入张量形状不对而报错、口型线程直接退出。
>
> ⚠️ 重新生成前先清空 `data/avatars/<人物>_lt`：新旧帧混在一起（例如旧的 150 帧 + 新的 115 帧）
> 会让播放出现乱序或尾部残影。`data/custom/<人物>_idle` 同理。

### 4.2 待机帧（不推理，纯播放）

把待机视频按固定帧率导出到 `data/custom/<人物>_idle/`，例如 240 帧左右、480p：

```powershell
ffmpeg -i "数字人\罗从彦待机动作.mp4" -vf fps=25,scale=-2:480 -q:v 2 "data\custom\luocongyan_idle\%%08d.png"
```

再写一份动作配置（每个待机片段一个条目）：

```json
[ { "audiotype": 1, "imgpath": "./data/custom/luocongyan_idle" } ]
```

## 5. 启动

```powershell
python app.py --transport webrtc --model wav2lip `
  --avatar_id jiangwanli_lt --customvideo_config custom_jiangwanli.json
```

服务起在 **8010**。仓库根目录的 `启动系统.bat` 会在检测到 `..\LiveTalking` 时自动带上这条命令；
如果不是同级目录，设置环境变量 `LIVETALKING_DIR` 指向实际路径即可。

## 6. 常见问题

| 现象 | 原因 |
|---|---|
| 页面里数字人黑屏 | `avatar_id` 对应的 `data/avatars/<id>` 不存在，或服务没起来 |
| 头像不动、只有声音 | 待机帧目录为空，或 `customvideo_config` 路径不对 |
| 一张嘴就报错 / 口型线程退出 | 人脸裁切尺寸不是 256×256，重新跑 `genavatar.py --img_size 256` |
| 说话时 CPU 占用很高 | 未应用补丁 2，torch 线程池没限制 |
| 待机画面来回倒放 | 未应用补丁 1 |

## 7. 性能提示

推理之外基本都是 CPU 活：每帧的梅尔频谱、帧拷贝、人脸贴合，以及 WebRTC 的 VP8/H.264 软编码。
GPU 常常在等 CPU 把下一批音频特征凑齐，所以「看着 GPU 利用率不高」是正常的。
补丁 2（限制 torch 线程）与「渲染线程不 sleep」都是围绕这条链路做的优化。

## 8. 为什么某个数字人说话时嘴部会发虚（实测结论）

2026-10 排查「王阳明说话时嘴部像马赛克、罗从彦正常」，结论如下（数值为实测）：

**成因排序**

1. **素材本身：嘴被胡须盖住**。wav2lip 每帧重绘的是**下半张人脸**，
   而王阳明的嘴几乎完全被浓密胡须包住（嘴唇几乎不可见）。模型对细密毛发只能给出
   低细节版本，贴回清晰原帧上就成了一块发虚的区域。
   同一指标下，王阳明素材嘴部区域锐度 **264**，罗从彦只有 **125**（越锐越"值得丢"）。
2. **人脸占比最大**：王阳明人脸框占画面宽 **30%**，罗从彦/朱熹约 22%，吕祖谦 20%。
   同样的处理损失，屏幕上被放大 1.4 倍后更明显。
3. **编码不是主因**。aiortc 的 H.264 默认 1 Mbps，但浏览器 REMB 反馈会把实际码率
   推到 2.1–2.7 Mbps（约 0.3 bit/像素，对 H.264 已属宽裕）。
   补丁 3 把上限提到 6 Mbps，主要收益是**开播头几秒**（REMB 爬坡之前）。

**可调的三处（已全部应用）**

| 手段 | 位置 | 实测收益 |
|---|---|---|
| 收紧人脸框（去掉帽子与下巴以下长胡须，143×214 → 143×154，宽高比 0.66 → 0.93） | `data/avatars/<id>_lt/coords.pkl` + `face_imgs` | 嘴部在 256×256 输入里的占比 +40% |
| 贴回改 `INTER_AREA` + 边缘 4–12px 羽化 | `avatars/wav2lip_avatar.py` | 人脸区锐度 +3.6%，胡须纹理肉眼可见恢复 |
| 码率上限 3 Mbps → 6 Mbps、起始 3 Mbps | `app.py`（补丁 3） | 开播首秒更清晰 |

**要说清的局限**：以上只能把损失压一点，**根治要看素材**——嘴唇不被浓密胡须遮挡
（或胡须更短更稀）时，模型才有依据还原口型。另一条路是换 MuseTalk：它只重绘嘴部
mask 区域而不是整块下半脸，对"胡须包住嘴"的素材友好得多，代价是要重新下载约 3.5 GB 权重。

**排查这类问题的方法**（可复用）：
1. 用 `coords.pkl`（顺序是 `y1, y2, x1, x2`）算人脸框尺寸与占画面比例；
2. 把 `full_imgs` 里嘴部区域归一化到同一高度后比锐度（拉普拉斯方差），判断是素材问题还是管线问题；
3. 设 `LT_LOG_BITRATE=1` 启动 LiveTalking，日志会打印编码器真实码率与 REMB 调整过程。

### 8.1 「说话时看着像没张嘴」（朱熹）

2026-10 实测：同一套直播画面里逐帧量嘴部区域的像素变化量——

| 人物 | 说话时 | 待机时 |
|---|---|---|
| 朱熹 | 2.61 | 2.85 |
| 罗从彦（对照） | 10.85 | 10.54 |

朱熹说话与待机几乎同值 → **不是模型没驱动，而是素材本身张嘴幅度就小**（他的白须又把嘴唇挡了大半）。
在 `avatars/wav2lip_avatar.py` 里加了 `MOUTH_GAIN` 表：

```python
MOUTH_GAIN = {"zhuxi_lt": 1.6}   # 默认 1.0，不写就不影响
```

它对**下半张脸**做差异增益 `out = orig + gain * (gen - orig)`，只放大模型真正动过的地方。
实测朱熹嘴部变化量 **2.61 → 6.85（2.6 倍）**，画面里能明显看到张嘴，且没有明显伪影。
要把幅度调更强/更弱只改这个系数；觉得放大出噪点就调回 1.0 或降到 1.3 左右。

**根治仍是素材**：重出一版"讲话动作"视频，让张嘴幅度像罗从彦那样明显、嘴唇不被胡须遮住。

### 8.2 收紧人脸框的实测收益（不总有用）

`scripts/retighten_face_box.py` 可以按新框重裁任意人物的 `face_imgs` + `coords.pkl`
（去掉头顶头饰与下巴以下过长的胡须，让嘴部在 256×256 输入里占比更大），原数据备份在
`<avatar>/_backup_before_tighten`，随时可回滚。改完要重启 LiveTalking 生效。

实测（12 帧连拍、同一问句）：

| 人物 | 框变化 | 嘴部动作量 | 嘴部锐度 |
|---|---|---|---|
| 王阳明 | 143×214 → 143×154（宽高比 0.66→0.93） | — | **+3.6%**（且胡须纹理肉眼可见变清晰） |
| 朱熹 | 104×143 → 102×100（宽高比 0.73→1.02） | +3.5% | −4.2% |

结论：**收紧框只对有"大幅头饰/长胡须"的素材有意义**（王阳明），对朱熹这种本来就紧凑的框
几乎没有收益（都在 ±5% 噪声内）——因为限制画质的是 wav2lip 嘴部生成器的分辨率上限，
而不是输入取景。朱熹的问题靠 8.1 的幅度增益解决更对症。
